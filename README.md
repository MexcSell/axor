# AXoR

A live explorer and recommender for Bittensor subnets, built for miners deciding where to mine. It reads every subnet straight from the chain, works out what miners actually earn, and ranks subnets against your hardware, budget and skills. It also flags subnets to avoid and subnets that show scam signals.

## Features

| View | What it shows |
|---|---|
| **Explorer** | Every subnet, refreshed from the chain every 3 minutes (server-sent events push updates to open browsers). Columns: subnet number and name, task, what miners do, miners (registered / max), earning miners, top and 2nd miner earnings per day, registration cost, what you need (hardware tier and software), emission (τ/day and share), emission cycle, immunity period, field, links, conditions, rent budget, 7-day price trend, created date, UID availability and risk. You can sort, filter, search, choose columns and export CSV. Click a row for full details and interactive 7-day charts of price, registration cost and emission. |
| **Recommend** | A ranking you control: hardware, owned vs. rented, monthly budget, TAO for registration, fields, risk tolerance, six factor weights and hard constraints. It always returns at least 5 subnets, each with the task, why it's recommended, what miners do, what you need, the budget (rent, registration, expected gross/net, payback) and how to become a top miner. |
| **Avoid & Caution** | *Avoid*: you can't profitably get in right now (registration closed, no UID, no emission, dust rewards, slow payback, price crash). *Caution*: workable, but with a specific trap (winner-take-all, high owner take, few earners, early-stage rules, capital at risk, outflows, very new). |
| **New** | Subnets registered in the last 4 months, newest first. |
| **Dashboard** | Where signed-in users land: TAO price, emission, net TAO flow, volume, open UIDs and new subnets; fund movers over 24h (emission, alpha price, TAO flow) as diverging bars; top opportunities (realistic earnings ÷ running cost × an estimated top-miner chance, UID open, no scam/avoid flags); your workspace subnets; today's daily note and PDCA counts; the latest notifications and subnet news. |
| **Notifications** | A bell in the header. After every chain update the server raises alerts for new subnets, emission up or down 25%+ in 24h, subnets that start qualifying as opportunities, fund moves (TAO ±5% and alpha ±20% in 24h, registration cost halved or doubled, a daily TAO-flow digest) and news for workspace subnets. Each user picks the kinds, can limit emission and fund moves to their workspace, and can turn on browser notifications. **Notifications** in the sidebar opens the full page: an inbox with filters, **push notifications** on every browser or phone you turn them on for (delivered by AXoR's own push server even when AXoR is closed), per-kind bell and push settings, quiet hours, an hourly cap, the push history, and for admins the push server and announcements (see [Notifications and push](#notifications-and-push)). |
| **Slack channel** | One channel of your Slack workspace, in the sidebar (shown as `#channel` with a count of new messages). Read the channel and its threads, post messages and thread replies, and share a subnet (drawer or workspace), one of your notes (note menu) or a notification. Posts are sent by the Slack app under each member's name and are escaped, so nobody can @channel through AXoR. Admins connect the app in the Slack view (token checked before saving, sudo required), choose which notification kinds are posted automatically, and can limit posting to admins. The server polls Slack once for everyone. |
| **Source hub** | Your team's GitHub repositories and their CI/CD, in the sidebar (with a count of repositories whose latest run failed). Per repository: **Code** (folders and files at any branch with line numbers and the folder's README; files that look like secrets, such as `.env` files, keys and wallets, are listed but their contents are never shown), **Actions** (workflow runs filtered by workflow and branch; open a run for its jobs, steps and log), **Commits** per branch with each commit's CI status, open **Pull requests** (jump to a PR's checks), **Branches**, **Workflows** and **Deployments**. Admins connect one or more **sources**, each a GitHub account, organization or GitHub Enterprise server with its own token (checked before saving, sudo required), add and delete sources (deleting one removes its token and its repositories from the hub), add or remove **several repositories at once** (tick them in the list the token can see, or paste owner/name or URLs), and **run workflows** (`workflow_dispatch`, with a form built from the workflow's own inputs), re-run all or failed jobs, cancel runs, and enable or disable workflows; each action is audited. Members can browse the chosen repositories, private ones included, but can't change anything. Only listed repositories can be reached through the token. The server calls GitHub with a short shared cache, and the page refreshes faster while a run is live. |

## How the numbers are computed

- **Miner earnings per day**: each UID's last-epoch emission is split into its miner part (incentive) and validator part (dividends). That is scaled to epochs per day and converted to TAO at the subnet's alpha price, with the owner hotkey excluded. Values are averaged over the last 24 hours of samples.
- **UID available**: registration is enabled, the interval rate limit hasn't been hit, and there is either an open slot or a non-immune UID that can be pruned.
- **Trends**: on first start the app backfills 7 days of price, registration cost, emission and volume from an archive node (4 points per day). After that, live samples are added every refresh and stored in SQLite. History from a previous subnet on a recycled netuid is ignored.
- **Recommendation score**: each subnet gets six factor scores. *Profit* is expected net USD per month: the median earner's pay × the share of miners who earn, minus rent and registration. *Accessibility* is fit with your hardware, budget and TAO, plus an open UID. *Fair competition* is how widely rewards are spread. *Stability* covers age, emission share, owner take and public code. *Momentum* is the 7-day price change and net TAO flow. *Skill fit* matches the fields you picked. Factors are percentile-ranked, combined with your weights, then multiplied by penalties for risk flags (scaled by your risk tolerance), unaffordable hardware and negative expected profit.
- **Hardware, software and rent budget** come from `backend/app/data/knowledge.json`. It was curated from each subnet's README and miner docs. Rent budgets are typical cloud prices for that hardware tier, not quotes.

## Security

- **Passwords** are hashed with Argon2id. They must be at least 12 characters and mix 3 character types (or be 16+ characters). Common passwords and passwords found in known breaches are rejected.
- **Two-factor authentication is mandatory.** You scan a TOTP QR code with an authenticator app during registration, and every sign-in needs a code. Codes can't be reused. You get 10 one-time recovery codes, stored hashed. Changing your password or issuing new recovery codes requires a current authenticator code.
- **Sessions** use a random 256-bit token, and only its hash is stored. The cookie is HttpOnly and SameSite=Strict, and also Secure on HTTPS. A session ends after 24 hours idle or 7 days at most. The token is replaced after each sign-in step. Changing your password signs out every other device, and there is a "sign out of all devices" button.
- **Abuse limits**:
  - Per-IP rate limits: 10 sign-in attempts per 5 minutes and 5 registrations per hour.
  - Per-account lockout: 15 minutes after 5 wrong passwords.
  - 5 wrong two-factor codes end the sign-in attempt.
  - Sign-in errors never reveal whether an email is registered.
- **Browser protections**:
  - A strict Content-Security-Policy with no inline scripts.
  - The Study Lab runs learners' Python in a Web Worker with its own policy: it loads Pyodide from one pinned jsDelivr path and packages from PyPI, and can't reach anything else, AXoR's API included, so code typed there can't act as the signed-in user.
  - Anti-CSRF: a custom request header plus a same-origin check.
  - Clickjacking protection with `frame-ancestors 'none'`.
  - `no-store` on API responses.
- **Use HTTPS in production.** Without it, passwords and session cookies cross the network unencrypted. Put a TLS proxy such as Caddy in front of the app.

## Drive

Files live in **AXoR Drive** (`drive/`), a small file server that runs as its own container with its own volume (`drive-data`). It has no published port: only AXoR talks to it, over the compose network, with a shared secret and the identity of the signed-in user. Browsers only ever talk to AXoR.

- **Spaces.** My drive belongs to one user; nobody else, admins included, can open it unless they share something. In the Shared drive everyone can read, upload (new files or new versions) and create folders. Renaming, moving, deleting and restoring old versions are for whoever added the item, or an admin. You can only move your own files into My drive.
- **Sharing with people.** The owner of a My drive file or folder shares it with accounts by username or email (there's no directory to browse), as **viewer** (open, download, copy) or **editor** (also add, edit and upload files, and rename, move or delete what's inside a shared folder). Sharing a folder shares everything in it. The shared item itself stays the owner's to rename, move, delete or share, and items shared with you can't be moved out of the owner's drive (make a copy instead). The folders above a shared item stay private: paths start at what was shared. Moving an item to the Shared drive ends its sharing. Anyone can remove something from their *Shared with me*. Sharing and unsharing are audited.
- **Versions and edits.** Uploading a file whose name is taken adds a version (or, if you choose *keep both*, a numbered copy); so do *Upload new version* and saving a text file in the editor. The last `DRIVE_VERSIONS` are kept. Restoring a version copies it on top, so nothing in the history is lost.
- **Copies, zips and thumbnails.** Copies share the stored data but count towards the copier's space. Folders and selections download as zips streamed while they're built (up to 10,000 items). Image thumbnails are made once per file (Pillow, in the drive image) for PNG, JPEG, GIF, WebP, AVIF, BMP and TIFF up to 120 megapixels.
- **Activity** records uploads, versions, edits, renames, moves, deletes, restores, copies, sharing and links per item for a year; a folder's activity includes what's inside it.
- **Storage.** Files are stored by content hash, so identical uploads take the space once. The quota counts every version a user uploaded, edited or copied, trash included, until it's emptied. Drive › Storage shows what takes it, by type, older versions and the trash, with your largest files.
- **Previews** are served from AXoR with a strict content policy. Only images, PDFs, audio and video are shown as themselves. Text, code and HTML are shown as plain text, and everything else downloads.
- **Share links** go to a public page on AXoR (`/s/<token>`) that downloads the file, or a folder as a zip, with an optional password (rate-limited) and an expiry of 1–90 days or never. Viewers of a shared item can't make links. Admins can see and revoke everyone's links and can stop members from creating them (Drive › Share links). Creating and revoking links is audited.
- **Workspace and agents.** The workspace Files panel lists the Shared drive and your My drive. Uploads from the workspace and the agent chat paperclip go to *Shared drive › Workspace*. Agents read attached files' text, including PDFs.
- **Migration.** On first start with the drive, files from the old built-in file hub (`DATA_DIR/workspace_files`) move into *Shared drive › Workspace*, keeping their uploader, subnet tag and date.
- **Back up** the `drive-data` volume alongside `scout-data`.
- **Updating** from an older drive: rebuild its image (`./scripts/run.sh --build` or `docker compose up -d --build`) for thumbnails. Its database gains the new tables on start, and Office files already in the drive are indexed for search then.
- **With `docker run` instead of compose**, put both containers on one network and share the secret volume:
  ```bash
  docker build -t scout-drive drive && docker network create scout-net
  docker run -d --name scout-drive --network scout-net --restart unless-stopped -v scout-drive-data:/data -v scout-drive-secret:/secret scout-drive
  docker run -d --name subnet-scout --network scout-net --restart unless-stopped -p 8000:8000 -v subnet-scout-data:/data \
    -v scout-drive-secret:/drive-secret:ro -e DRIVE_URL=http://scout-drive:8100 -e DRIVE_SECRET_FILE=/drive-secret/drive.key subnet-scout
  ```
  Admins see **Drive** in the sidebar even before it's connected, with these steps.

## Notifications and push

**Notifications** in the sidebar (`#notifications`) gathers everything about notifications; the bell's popover links to it.

- **Inbox**: every alert in the bell, filtered by kind or unread, with older ones on demand.
- **Devices**: *Turn on push* on each browser or phone you want notifications on. AXoR then reaches it even when no AXoR tab is open, and opens the subnet or page the notification points to when you click it. Each device can be renamed, tested and removed; the one you're on is marked.
- **Settings**: per kind, whether it shows in the bell and whether it's pushed (push only sends what's in your bell); only-my-workspace moves; browser pop-ups while AXoR is open; quiet hours in your own time zone; at most 1–60 pushes an hour. Alerts raised together after one chain update arrive as one push.
- **History**: every push sent to your devices and whether it arrived, failed, or the browser had ended the subscription.
- **Server** (admins): the push server's state, devices by push service, the public key, recent messages with their deliveries, every device on the server (removing one needs sudo), and **announcements**: a title, message and link sent to everyone, admins or chosen users, optionally posted to everyone's bell, optionally urgent (through quiet hours and hourly caps). Sending needs sudo and is audited.

Push is AXoR's own: a separate **push** service (`push/`, [Web Push](https://www.rfc-editor.org/rfc/rfc8030)) keeps the subscriptions and this server's VAPID key pair (made on first start, kept on its volume; replacing it ends every subscription) and delivers each message encrypted for the receiving browser (RFC 8291) and signed with that key (RFC 8292). Browsers only accept push through their maker's push service (Google's for Chrome, Edge and Chromium, Mozilla's for Firefox, Apple's for Safari), so the push server needs outbound internet; those services relay ciphertext only. Subscriptions may only point at the hosts in `PUSH_HOSTS`, over HTTPS, at public addresses, so a made-up endpoint can't aim the push server at internal hosts. A device the push service reports gone is removed at once, and one that fails `PUSH_MAX_FAILS` times in a row is removed too.

Browsers only allow push on HTTPS pages (or `localhost`): behind a plain `http://` address the Devices tab says so and the bell keeps working. On iPhone and iPad, add AXoR to the Home Screen and turn push on from there. The service worker is `frontend/sw.js`; it shows notifications and handles clicks, and caches nothing.

## Agents

The **Agents** tab (in the sidebar under Tools) hosts AI agents. It's for admins unless an admin turns on **Members can use agents** in Agents → Models.

**Models.** Agents run on **Claude** (Anthropic API), **OpenAI**, **OpenRouter** (Gemini, Llama, DeepSeek, Mistral and hundreds more behind one key; only models with tool calling are listed), a **local** OpenAI-compatible server (Ollama, LM Studio, vLLM, llama.cpp), or **Terminal**: the Claude Code CLI on the server, signed in with its own Claude login, no API key. Connect any of them in **Agents → Models**.
- Keys and URLs are verified first (a model list call, which costs nothing), then stored encrypted on the server with Fernet. The encryption key is `DATA_DIR/secret.key`, or `SECRET_KEY` if set.
- Browsers only ever see a masked form such as `sk-ant-…WXYZ`. Connecting or removing a provider needs the admin confirmation step and is audited.
- Settings saved in the UI take priority over the `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY` and `LOCAL_LLM_URL` environment variables.
- The model picker in each chat (and drill, tutor and board assistant: one choice for all of them) offers every connected model, **Auto** (the default model an admin picks, otherwise Claude), and **Deep thinking** (low, medium, high, shown as bars on the pill). You can switch models in the middle of a chat; each answer shows which model wrote it and its tokens.
- **Usage:** the meter in every composer shows this chat's tokens; open it for yours today, this week and this month, the last 14 days, and the month by model and by feature (agent chats, workspace, tutors, drills, project team, board assistant).
- **Terminal** runs `claude -p` once per model turn as the user that runs AXoR, so that user must have run `claude` once and logged in (`claude auth status` shows it). Connecting checks the CLI is installed and signed in. Prompts go in on stdin from an empty temporary folder, with the CLI's own tools (shell, files, web), MCP servers, hooks, plugins and CLAUDE.md turned off; any API key in the environment is withheld, so usage counts against the Claude Code login. Agent tools still work: the CLI returns tool calls as structured output and AXoR runs them. Pick Fable, Opus, Sonnet or Haiku (the CLI resolves each alias to the latest model). The Docker image includes the CLI (pin a version with the `CLAUDE_CODE_VERSION` build arg). A container can't see your machine's login, so run `claude setup-token` once (it opens a browser sign-in to your Claude account and prints a long-lived token tied to your plan, not an API key), put it in `.env` as `CLAUDE_CODE_OAUTH_TOKEN=…`, and run `docker compose up -d`. Without Docker, the login of the user that runs AXoR is used as is.
- **Codex** is the second terminal provider: `codex exec` (OpenAI's Codex CLI) once per model turn, on the ChatGPT plan it is signed in with, not an API key (that's the OpenAI provider). Each turn runs from an empty temporary folder with a read-only sandbox, `--ignore-user-config --ignore-rules --ephemeral`, the agent's system prompt in place of Codex's own (`model_instructions_file`), and the CLI's tools off (shell, code mode, web search, browser, apps, plugins, sub-agents); `OPENAI_API_KEY` is withheld. Tool calls are native by default (Agents → Models → OpenAI (Codex) CLI → Tool calls): one `codex exec` session per agent run gets AXoR's tools through the same private MCP server as Terminal's native mode (`codex_bridge.py`), pre-approved for that server only; Codex calls them from its code mode, a bare V8 runtime with only the tool bindings (no files, network or processes), so the image also ships `codex-code-mode-host` next to `codex`. Codex reports tokens when a run ends. In text mode tool calls come back as strict structured output (each input as a JSON string) and AXoR runs them. Structured answers whose schema strict mode can't take fall back to plain JSON. Models are read from the CLI's models cache, plus Codex's default. It has its own parallel limit and usage-limit clock: a "You've hit your usage limit" holds Codex teams in Autoloop until the reset, not Claude ones. The image includes the CLI (pin it with the `CODEX_VERSION` build arg). Sign it in once where `CODEX_HOME` is kept: `kubectl -n axor exec -it deploy/web -- codex login --device-auth` (Docker: `docker compose exec subnet-scout codex login --device-auth`), then connect Codex in Agents → Models.
- **Local server in Docker:** the container can't reach `localhost` on your machine. Use `http://host.docker.internal:11434/v1` (Ollama) and start the container with `--add-host=host.docker.internal:host-gateway` (docker-compose.yml already does). Local models need tool calling support for agents to look things up (e.g. Llama 3.1+, Qwen 2.5+).

**Custom agent chats** are laid out like a chat with a teammate:
- **Chats and activity** on the left (search, rename or delete a chat from its title menu), with **Connect channels** (share answers to the Slack channel), **Brain** (instructions, skills, tools and memory) and **Give feedback** (lands in the admin audit log).
- The header shows the agent's face and "Name, Role", **Share** (people and the directory), **copy link** (`#agents/<id>` opens that agent's chat) and a **⋯** menu: Memory, Pause/Resume, Duplicate, Edit, Delete.
- The agent opens a new chat with a greeting and suggested replies; every answer ends with up to three suggested follow-ups and has **read aloud**, **copy**, 👍/👎, **share to Slack** and its model and token use.
- **Memory:** each agent keeps short facts per user across chats (it saves them with a `remember` tool, or you add them with `/remember …` or the Memory dialog). You can see and delete them; people an agent is shared with have their own memory.
- Every chat (Agents, Workspace and Study) shares one message UI. The composer has **+** to upload a file (to the Shared drive), pick an **AXoR Drive** file or **Source code** (a file or folder of a Source hub repository), and in Agents a skill (applied to that answer) or a tool (to use); **@** to mention them while typing; **/** commands (Agents: `/new`, `/remember`, `/memory`, `/rename`, `/brain`, `/share`, `/help`; Study: `/new`, `/next`, `/quiz`, `/plan`, `/testout`, `/material`; Workspace: `/new`, `/brief`, `/news`); voice input; the model pill and the usage meter. Attached text is read up to 20,000 characters per file, six attachments a message.
- Answers render Markdown with code blocks you can copy and links; long answers fold; your own messages can be edited and resent. **Chat display** (the **T** button) sets text size, spacing, bubbles or a document layout, and Enter or Ctrl+Enter to send, for every chat. The Study and Workspace chats can be widened or resized by dragging their left edge.

**User administration agent:** ask in plain language, for example "security summary for the last 24h", "who has no 2FA?", "why can't alice sign in?" or "lock down sign-ups".
- **It investigates with read-only tools:** security overview, user list with filters, a user's details and events, and audit log search.
- **It can only propose changes.** Account actions and sign-up/sign-in settings appear as approval cards. Nothing runs until an admin clicks **Approve**. That click requires the same confirmation step as the Admin tab, and the server applies the same safeguards (no self-actions, last admin protected).
- **Approved actions are audited** with the detail `agent`. Their outcome is reported back to the agent on your next message.
- **Conversations are stored on the server, per admin.** One-time passwords from approved resets are shown only to you, never sent to the model.
- **The tool loop runs on the server.** Refusal fallbacks are enabled (`fallbacks: "default"`).

**The agent core** (`agent_core.py`): every agent system (your agents and the built-in ones, Agent HQ, the project team, Workforce, the Company, Mission OS, Long tasks, Competition teams and the Workflow) keeps its own process and page, and shares one core underneath. One registry: every agent under one key (`workforce:12`, `teams:5`), mirrored from each system's tables. One run ledger (`ac_runs`): each engine opens a run where its work starts and closes it where it ends; every model call made on that thread adds its tokens (`llm.py`), a chat outside any run is written by `log_usage`, and the Workflow's runs on the host are recorded with their cost. One budget: a per-user daily token limit (Agent Operations → Daily budget, off by default) checked before every model call in a run. Agent Operations, the workspace Overview and the Ecosystem read the ledger.

**Operations agents** (`ops_agents.py`): five more built-in agents for admins. They work the same way: read tools run at once, and changes are approval cards. They show under **Built-in agents** on the Agents home, with a **Not set up** badge when their service isn't on this server.
- **DevOps:** pipelines, runs, step and app logs, and the Source hub's CI. It proposes runs (any branch, tag or commit), rollbacks to a successful run, cancels, and app start, stop and restart.
- **Functions:** each function's code, settings, logs and call statistics. It proposes new functions, code changes (you review a diff), test calls (the answer appears on the card and goes back to the agent), restarts, stops and rollbacks. A code change is refused if the function changed after the agent read it.
- **Apps:** status, pods, events, revisions and logs. It proposes a new image and/or replica count (everything else stays), restarts, stops and rollbacks.
- **Cluster:** nodes, deployments, problem pods, warning events, pod logs (also the run before a crash), and this server's CPU, memory and disk. It proposes restarts, scaling and pod recycling. `kube-system` stays read-only, and AXoR can't stop itself.
- **DNS:** zones, records, lookups and delegation checks. It proposes adding, changing and removing records. Records the platform or ACME keeps are off limits.
- **Secrets never reach the model.** Agents see environment variable names, never their values, and secret values are masked in logs. Approving runs the page's own operation with its checks and audit entry, plus an `agent.approve` entry.

**Assist** (`assist.js`, `assistant.py`): an agent beside every page. The **Assist** button in the top bar opens a panel on the right. On wide screens it sits beside the page; on narrow ones it covers it.
- **The page's own agent.** For admins: DevOps on DevOps and Source, Functions, Apps, Cluster on Cluster, System and Machines, DNS, and User admin on user administration. Everywhere else, and for members, it's the **Assistant**.
- **The Assistant** is a built-in agent for everyone who can use agents. It knows AXoR's pages and reads subnets, your workspace, your study progress and the Source hub (admins also get DevOps pipelines). It changes nothing.
- **Other agents.** The menu in the panel's header switches to another built-in agent or one of your own. The choice is remembered per page.
- **Page context.** Each message says which page it was sent from (`pages.py`), so "this page" means the one you're on.
- **Chats.** They're the same chats as in the Agents tab. **Open in Agents** continues one there, and the panel reopens your last chat with each agent. Proposals are approved right in the panel.

## User administration

Admins see an **Admin** tab with:
- account statistics: users, two-factor coverage, active sessions, and sign-ins and failures in the last 24 hours
- a switch to open or close public registration
- a searchable user list showing role, status (active / disabled / locked / temporary password), two-factor state and recovery codes left, last sign-in and IP, active sessions, and join date
- per-user actions: make or remove admin, unlock, sign out all devices, reset password (shows a one-time temporary password that must be changed at next sign-in), reset two-factor, disable or enable, delete
- an audit log of registrations, sign-ins, failed attempts, password changes and every admin action, with the actor and IP

**Safeguards:**
- Any change to another account asks for the admin's authenticator code, which stays valid for 10 minutes.
- Admins can't change their own role or status from the admin page.
- The last active admin can't be demoted, disabled or deleted.
- Only users who have finished two-factor setup can become admins.

**Roles:**
- **admin**: everything a user can do, plus the Admin tab.
- **user**: the explorer, recommendations and their own account settings.

**Create the initial admin** with any one of these:

```bash
# 1. Create a new admin account (prints a one-time password)
docker exec subnet-scout python -m app.create_admin admin            # or an email

# 2. Or promote an account that already registered and finished 2FA
docker exec subnet-scout python -m app.promote alice                 # username or email
```

3. Or set `INIT_ADMIN_EMAIL` (and optionally `INIT_ADMIN_PASSWORD`) before the first start.

A created admin's first sign-in uses the one-time password. It then sets up the authenticator app, saves the recovery codes and requires a new password, so the one-time password stops working after that first use.

## Docker management

Admins can manage the server's containers and images from **Docker** in the sidebar (under Tools; also in the account menu, or `#docker`):
- engine version, running containers, and total CPU and memory in use
- a container list with state, image, published ports, live CPU and memory (refreshed every 15 seconds), and compose project. You can view logs (last 100–5000 lines, copyable), start, stop, restart and remove containers.
- an image list with tags, size and how many containers use each one. You can pull an image by name, remove an unused image, and prune dangling images (optionally every unused image).

AXoR never mounts the Docker socket. A separate **docker-proxy** service ([wollomatic/socket-proxy](https://github.com/wollomatic/socket-proxy)) holds it and passes on only the requests this page makes. The proxy itself refuses creating or running containers, `exec`, builds, volumes, networks and every other API, so even a compromised AXoR can't start a privileged container on the host. The proxy is on a private network that only AXoR can reach, it publishes no port, and it runs read-only with every capability dropped. It's opt-in:

```bash
stat -c %g /var/run/docker.sock                  # the socket's group id, e.g. 999
echo DOCKER_GID=999 >> .env
docker compose --profile docker up -d            # or COMPOSE_PROFILES=docker in .env
```

**Safeguards:**
- Every change (start, stop, restart, remove, pull, image removal, prune) asks for the admin's authenticator code (sudo, valid for 10 minutes) and is written to the audit log.
- AXoR's own container can't be changed from the page. The drive and the proxy (label `scout.protected`) can be restarted but not stopped or removed.
- Running containers must be stopped before they can be removed, and images in use by a container can't be removed (nothing is forced).

Even so, an admin can stop or remove any other container on the host, so keep the profile off on shared servers. Outside Docker, set `DOCKER_URL=unix:///var/run/docker.sock` to talk to the socket directly; this skips the proxy's protection.

## DevOps

Admins can build, test and deploy Source hub repositories on this server from **DevOps** in the sidebar (`#devops`). A pipeline is one app: a repository and branch, its Dockerfile, an optional test command and, to deploy it, the container port, the host port (within `RUNNER_PORTS`), a health check path, memory, CPUs, a volume, environment variables and secrets. A run downloads the commit, builds the image, runs the tests in a throwaway container, then swaps the app's container and checks its health, rolling back if it fails. Runs start by hand, on new commits (auto deploy) or as a rollback to an earlier run's image.

AXoR never gets the Docker socket for this. A separate **runner** service (`runner/`) is the only part allowed to build images and create containers, and it sets up every container itself: not privileged, no host paths or host network, capped memory, CPU and processes, on its own `axor-apps` network. It only touches containers, images and volumes it labelled `axor.devops`. AXoR reaches it over an internal network with a shared secret.

```bash
stat -c %g /var/run/docker.sock                  # the socket's group id, e.g. 999
echo DOCKER_GID=999 >> .env
docker compose --profile devops up -d            # or ./scripts/run.sh, which starts it unless --no-devops
```

Every change (pipelines, runs, cancels, rollbacks, starting and stopping apps) needs sudo and is audited. Secrets are stored encrypted and masked in logs. The runner holds the socket read-write, which is root on the host if it's compromised, so keep the profile off on servers where you don't need it.

## Kubernetes, HTTPS and DNS

AXoR can run on Kubernetes ([k3s](https://k3s.io), single node) instead of Docker Compose. There it serves everything over HTTPS through its own edge (Traefik), answers DNS for its own zones with **AXoR DNS** (`dns/`, its own service), and gives admins five more pages under Tools:

| Page | What it does |
|---|---|
| **Cluster** (`#cluster`) | The node's CPU, memory and pods; each AXoR namespace with its deployments (ready, image, restarts, CPU, memory; restart, stop/start, logs) and pods (logs, also before the last restart; recycle); recent warnings. **Domain & HTTPS**: the platform domain, AXoR's address on it, Let's Encrypt on or off (staging too), AXoR's root certificate to download, the edge certificate, a check that the domain is delegated to AXoR DNS, and a sync. **Updates**: the updater that deploys each new commit on main (below): what runs, what's waiting, the last updates and their log; check now, update now, pause. |
| **Apps** (`#apps`) | PaaS: run any container image with HTTPS at `https://<app>.apps.<domain>/`, custom domains, replicas or CPU autoscaling, CPU and memory limits, environment variables and secrets, a health check, a command, a persistent volume. Overview (status, pods, events), Test (a request sent from inside the cluster), Logs, Revisions (roll back). |
| **Functions** (`#functions`) | FaaS: write a Python 3.12 or Node.js 22 handler in the page; it answers at `https://<fn>.fn.<domain>/`. Packages (installed at start), environment and secrets, timeout, replicas or autoscaling. Code (edit and deploy), Invoke, Logs, Revisions, Stats (calls, errors, median and 95th percentile duration, calls per minute). |
| **Machines** (`#machines`) | Linux and Windows virtual machines on the server's KVM. Linux: Ubuntu (Desktop or Server), Debian, Fedora, CentOS Stream, Rocky, AlmaLinux, openSUSE, Arch, Alpine, Kali, Mint, Manjaro, NixOS, or any ISO or disk image by URL. Windows: 11, 11 LTSC, 10, Server 2025, 2022 and 2019, installed unattended with the account, password and language set here. CPU cores, memory and a disk that outlives restarts. Console (the machine's screen in the page, with Ctrl+Alt+Del, fit or 100%, full screen), Overview (system, resources, disk, pod, events, setup progress), Logs; start, stop (a clean shutdown), restart, edit, delete. |
| **DNS** (`#dns`) | AXoR DNS's zones and records (A, AAAA, CNAME, MX, TXT, NS, SRV, CAA, wildcards): add, edit, delete, zone settings, BIND import and export, a query tool that shows the answer like `dig`, a delegation check against public resolvers, query statistics. |

**Domain and certificates.** Until an admin sets a domain the platform uses `axor.internal`, which only AXoR DNS answers for. AXoR answers at the domain (or a name under it), apps at `*.apps.<domain>`, functions at `*.fn.<domain>`; AXoR keeps those records in AXoR DNS itself (marked *Platform* on the DNS page). AXoR's own certificate authority signs the edge's certificate for all of them and the server's IP. Its key is kept encrypted in AXoR's database and it is **name-constrained** to the platform domain, so trusting its root (Cluster → Domain & HTTPS) can't let anyone impersonate other sites. With a public domain delegated here (at the registrar: name servers `ns1.<domain>` and `ns2.<domain>`, glue records pointing at the server), switch on Let's Encrypt: the edge gets one certificate for the domain, `*.apps` and `*.fn` over DNS-01, answered by AXoR DNS (so no port 80 is needed), and one per custom domain (DNS-01 if AXoR DNS has its zone, TLS-ALPN-01 on port 443 otherwise).

**AXoR DNS** answers only for its zones: no recursion (so it isn't an open resolver), zone transfers refused, `ANY` answered the RFC 8482 way, UDP answers truncated to 512 bytes or the client's EDNS size (at most 1232) so big ones go over TCP, and UDP answers rate-limited per client network (`DNS_RATE`, 50 a second) with every other excess answer sent truncated, so it can't amplify floods. AXoR manages it with a shared secret; the edge has a second secret that can only place `_acme-challenge` records, which expire after ten minutes.

**Apps and functions** are Kubernetes Deployments, Services and Ingresses in `axor-apps` and `axor-functions`, labelled `axor.dev/app` / `axor.dev/function`; their settings live in the Deployment's annotations. Every deploy is a revision, and the environment (and a function's code) is a new immutable Secret (ConfigMap) named after its hash, so rolling back restores image, code and environment together; the last 10 revisions are kept. Scaling isn't a revision. A function runs on the stock `python` or `node` image under AXoR's small bootstrap (`backend/app/faas/`): non-root, read-only root file system, no capabilities. Deploys roll without downtime (a new pod is ready before the old one goes), except for apps with a volume.

**Machines** are KVM virtual machines: QEMU in a container, one pod per machine in `axor-machines` (`backend/app/machines.py`, `k8s/base/55-machines.yaml`). Linux runs on [qemux/qemu](https://github.com/qemus/qemu), which downloads the distribution's installer or live image at first start; install it from the Console as on a new PC (Arch comes ready-made: `arch` / `arch`). Windows runs on [dockurr/windows](https://github.com/dockur/windows), which downloads Windows from Microsoft and installs it unattended (10 to 20 minutes after the download). Windows 10 and 11 run unactivated and Server as a 180-day evaluation: activate them in Windows with your own licence. The disk is a volume (`<name>-disk`, its size plus 16 GB for the installer image) that only deleting the machine removes. The pod gets `/dev/kvm` from a small KVM device plugin (the resource `axor.dev/kvm`, 8 machines at a time) and nothing else from the host. The VM's network is user-mode ([passt](https://passt.top)), so it reaches what its pod may reach. The Console is [noVNC](https://novnc.com) (`frontend/vendor/novnc`, 1.7.0) talking over a WebSocket to AXoR, which relays it to QEMU's VNC port through the machine's Service. A machine's system, disk and Windows account are set when it's made; editing its CPU or memory restarts it.

**Security model.**
- **AXoR's own Kubernetes account** (`axor/web`, `k8s/base/10-rbac.yaml`) can read its namespaces and `kube-system`, restart and scale deployments, and recycle pods. It can create workloads only in `axor-apps`, `axor-functions` and `axor-machines`. A ValidatingAdmissionPolicy (`axor-system-changes`) makes sure that in AXoR's own namespaces a change is a restart or a scale and nothing else (no image, command, environment, annotation or security change), so even a compromised AXoR can't change what its services run.
- **The `axor-workloads` policy** holds every app, function and machine pod to CPU and memory limits, no Kubernetes API token, the namespace's default account, and config map, secret, scratch or own-volume mounts only.
- **Pod Security** enforces `baseline` for apps and machines (any image, even root ones, but no privileges, added capabilities or host access) and `restricted` for functions and AXoR itself.
- **KVM** reaches machine pods only through the device plugin (`kube-system/axor-kvm`, itself unprivileged: it only looks for `/dev/kvm` and registers with the kubelet). The quotas give `axor-apps` and `axor-functions` none of it, and `axor-machines` 8.
- **Network policies:** apps and functions can be reached only from the edge, from AXoR (Test and Invoke) and from their own namespace. They can reach the internet, cluster DNS and the edge, but not AXoR, this host, the Kubernetes API or any private range. A machine's screen (QEMU's VNC port) answers only AXoR's Console relay; other machines reach its SSH and RDP ports and nothing else. Machines reach out like apps, minus the edge. Opening a console needs an admin session with sudo, and is audited. AXoR DNS's API answers only AXoR and the edge.
- **The cluster** (`k8s/install-k3s.sh`) runs without k3s's bundled Traefik and ServiceLB, with host-gw networking (no VXLAN port) and Secrets encrypted at rest. The API server (6443) and kubelet (10250) only answer this host and its pods: an `AXOR-K3S` iptables chain, restored by a systemd drop-in each time k3s starts.

Reads need an admin session; changes need sudo and are audited (`cluster.*`, `update.*`, `app.*`, `function.*`, `machine.*`, `dns.*`, `platform.*`).

```bash
sudo ./k8s/install-k3s.sh      # once: k3s with the settings above (k3s-uninstall.sh removes it; see the script's header)
sudo ./k8s/deploy.sh           # build the images, load them into k3s, apply k8s/base; again after every change
sudo ./k8s/cutover.sh          # move the live AXoR over (below)
sudo ./k8s/auto-update.sh --install   # deploy each new commit on main by itself (below)
sudo ./k8s/redeploy.sh         # deploy.sh with checks around it: before, build + offline boot + unit tests; after, verify or roll back
tests/run-unit.sh              # the unit tests (tests/unit), inside the web image: production's exact dependencies, offline
```

**Before a deploy swaps AXoR** (`redeploy.sh`, and the updater for each new commit), the way AgentForge's supervisor swaps in a new version: the new web image must boot offline and pass the unit tests (`tests/run-unit.sh --image TAG`); a failure deploys nothing. Then it waits until the running AXoR reports no agent mid-task: `/api/health` returns `busy`, the agent tool loops and model calls in flight (`backend/app/busy.py`). It waits up to `DRAIN_MAX` seconds (600), then deploys anyway with a warning; `redeploy.sh --force` skips the wait. Work that resumes by itself after a restart (missions, long tasks, the Autoloop) is counted only while a model call runs.

`deploy.sh` reads AXoR's settings from `.env` (into the Secret `axor-env`; `DRIVE_*`, `PUSH_*` and `RUNNER_*` also go to those services), makes the shared secrets once, and never opens a host port: before the cutover the edge only answers inside the server (`curl -k --resolve axor.internal:443:<edge ClusterIP> https://axor.internal/`).

**Cutover.** `k8s/cutover.sh` redeploys with the DevOps runner and the Docker page's proxy (`k8s/host/`), stops the Compose containers, copies their volumes (`subnet-scout-data`, `scout-drive-data`, `scout-push-data`) into the cluster's volumes (what those held goes to `/var/lib/axor/cutover-<time>`), and maps the host's ports:
- **443** to the edge.
- **53** UDP/TCP to AXoR DNS, on the public IPv4 address only, so the server's own resolver keeps working.
- **8000**, AXoR's old address, now a redirect to HTTPS.

Port 80 stays with nginx unless you add `--http`. Later deploys keep the ports. `./k8s/cutover.sh --rollback` closes them, stops AXoR on k3s and starts the Compose containers again on their untouched volumes.

**Automatic updates.** `k8s/auto-update.sh --install` keeps AXoR up to date by itself. It adds a systemd timer (`axor-auto-update.timer`) that runs a pass every minute, and a clean checkout of the repository in `/var/lib/axor/update/src`. Every 3 minutes a pass fetches the branch (`main`, or `--branch <name>`). When there's a newer commit, it deploys it with `deploy.sh` from that checkout, never from a working tree, using the `.env` it was installed with. It checks that AXoR runs the new tag and answers `/api/health`. If the build, the rollout or that check fails, it rolls back: it applies the commit before again with its images (k3s keeps the last three tags), or undoes the deployments when that commit isn't on GitHub. That commit isn't tried again until a newer one lands or an admin asks. Each update's log is kept in `/var/lib/axor/update/logs` (the last 30). Before `deploy.sh`, it runs the commit's own `redeploy.sh --check` (images, offline boot, unit tests): when that fails, nothing is deployed and the update is recorded as **Checks failed**; then it waits for agents mid-task, as above.
- **It only moves forward.** It deploys when the running commit is in the branch's history. After a deploy by hand of other work (a working tree, another branch), it waits until the branch includes that work, for example a merge. After a squash merge, an admin can deploy the branch anyway.
- **One deploy at a time.** `deploy.sh` and the updater share a lock (`/run/axor-deploy.lock`): a deploy by hand waits for an update that's running, and the updater skips its pass while a deploy by hand runs.
- **Cluster → Updates** shows the running and newest commits, the commits waiting, the last updates with their log (live while one runs), and whether the updater is still reporting. From there admins can check now, update now, pause automatic updates, or deploy the branch anyway. AXoR never builds or deploys itself. It reads the updater's status (ConfigMap `axor-update-status`) and writes only requests (ConfigMap `axor-update`, the one object in its namespace it may change). The updater picks them up within a minute. Updating and pausing need sudo and are audited (`update.*`).
- `./k8s/auto-update.sh --status` shows the same on the host, `--dry-run` checks without deploying, and `--uninstall` removes the timer. `/etc/axor/auto-update.env` holds `BRANCH`, `ENV_FILE` and `CHECK_EVERY` (seconds between fetches). After a successful update, the next pass runs the `auto-update.sh` that came with the new commit.
